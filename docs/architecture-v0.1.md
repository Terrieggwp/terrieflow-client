# TerrieFlow Client Architecture — Version 0.1

## Статус документа

Этот документ адаптирует общее архитектурное направление TerrieFlow Client к версии `0.1` — UI-прототипу без реальных сетевых и VPN-подключений.

Документ не выбирает язык, UI-фреймворк, VPN-движок или целевую платформу. Эти решения принимаются отдельно и фиксируются в ADR.

## Цель версии 0.1

Версия `0.1` должна позволить быстро проверить:

- структуру основных экранов;
- навигацию и пользовательские сценарии;
- отображение пользователя и подписки;
- просмотр и выбор сервера;
- выбор режима подключения;
- состояния mock-подключения;
- обработку loading, empty и error-состояний.

Версия `0.1` не является VPN-клиентом и не должна создавать впечатление, что выполняет реальное защищённое подключение.

## Обязательные ограничения

- Используются только mock-данные.
- Отсутствуют обращения к production и test API.
- Отсутствуют реальные VPN-конфигурации и subscription URL.
- Отсутствуют настоящие access tokens, refresh tokens и UUID.
- `VpnEngine` реализуется только как mock и не создаёт сетевой интерфейс или туннель.
- `SecureStorage` реализуется только как mock и не хранит реальные секреты.
- Запрещено копировать production-данные в fixtures, screenshots, snapshots и документацию.
- Запрещено добавлять production endpoints даже как неиспользуемые константы.
- Логи и сообщения об ошибках не должны содержать значения, похожие на реальные секреты или конфигурации.
- Mock-режим должен быть очевидно обозначен в development-сборке и в диагностическом представлении.

## Принцип адаптации

Общая архитектура сохраняется как направление, но в `0.1` её слои являются логическими границами внутри одной сборки, а не обязательными отдельными модулями.

Для одного разработчика важнее сохранить правильное направление зависимостей, чем заранее создавать сложную модульную структуру. Новая абстракция добавляется только тогда, когда она:

1. защищает критичную будущую границу;
2. позволяет заменить mock на реальную реализацию;
3. делает значимый сценарий проще для тестирования.

## Минимальная архитектура

### 1. UI

Отвечает за:

- экраны и переиспользуемые визуальные компоненты;
- навигацию;
- отображение состояния;
- обработку пользовательских действий;
- локальные UI-состояния, не являющиеся бизнес-правилами.

UI не обращается напрямую к mock-данным и не управляет таймерами mock-подключения. Он получает данные и команды через сценарии или единый контроллер состояния приложения.

### 2. Core

Объединяет минимальные части Domain и Application в одну логическую зону.

Содержит:

- простые модели `User`, `Subscription`, `Server` и `Connection`;
- режим подключения;
- минимальный автомат состояния `Connection`;
- пользовательские сценарии;
- интерфейсы будущих внешних зависимостей;
- безопасные категории ошибок.

В версии `0.1` нет необходимости физически разделять Domain, Application и Ports на разные пакеты или сборочные модули. При этом Core не должен импортировать UI, mock-реализации или платформенные SDK.

### 3. Mock adapters

Реализуют интерфейсы Core с использованием только синтетических данных в памяти.

Содержат:

- mock-авторизацию;
- mock-подписку;
- mock-список серверов;
- mock secure storage;
- mock VPN engine;
- управляемые задержки и заранее определённые ошибки для демонстрации UI-состояний.

Mock adapters не выполняют HTTP-запросы, не открывают сокеты и не обращаются к системным VPN API.

### 4. Bootstrap

Единственная точка, где создаются mock-реализации и передаются сценариям приложения.

Bootstrap должен:

- всегда выбирать mock-окружение для `0.1`;
- не содержать production endpoints;
- централизовать время жизни состояния;
- позволять позднее заменить реализации без изменения UI и Core.

Полноценный DI-контейнер не требуется. Достаточно явной и легко проверяемой сборки зависимостей.

## Направление зависимостей

```text
UI -> Core interfaces and use cases <- Mock adapters
                    ^
                 Bootstrap
```

Core не зависит от UI и Mock adapters. Mock adapters зависят от интерфейсов Core. Bootstrap знает о конкретных реализациях, но не содержит бизнес-правил.

## Минимальные пользовательские сценарии

Для `0.1` достаточно следующих сценариев:

1. Показать экран приветствия.
2. Выполнить mock-вход.
3. Показать mock-пользователя и mock-подписку.
4. Показать список mock-серверов.
5. Выбрать сервер.
6. Выбрать режим подключения.
7. Запустить mock-подключение.
8. Показать переход `disconnected -> connecting -> connected`.
9. Остановить mock-подключение.
10. Показать заранее определённую безопасную ошибку.
11. Выполнить mock-выход и очистить состояние текущей сессии.

Синхронизация с сервером, восстановление реального системного VPN-состояния и работа в background не входят в `0.1`.

## Минимальная доменная модель

### User

Содержит только синтетический идентификатор и отображаемые поля, необходимые UI.

Требования:

- идентификатор имеет очевидный mock-формат, например `mock-user-001`;
- идентификатор не должен выглядеть как настоящий UUID;
- модель не содержит токены и данные аутентификации.

### Subscription

Содержит минимальные данные для отображения:

- synthetic ID;
- статус;
- условную дату окончания;
- безопасные mock-ограничения или возможности.

Subscription URL отсутствует даже в mock-модели `0.1`, поскольку UI-прототипу он не нужен.

### Server

Содержит:

- synthetic ID;
- отображаемое имя;
- регион;
- mock-статус доступности;
- поддерживаемые mock-режимы;
- необязательные демонстрационные показатели.

`Server` не содержит endpoint, IP-адрес, ключи или VPN-конфигурацию.

### Connection

Содержит:

- выбранный server ID;
- выбранный режим;
- текущее состояние;
- безопасный код mock-ошибки, если она возникла.

Минимальные состояния:

- `disconnected`;
- `connecting`;
- `connected`;
- `disconnecting`;
- `error`.

Состояние `preparing`, системные разрешения, reconnect и восстановление после завершения процесса откладываются до реальной платформенной интеграции.

### VpnConfiguration

`VpnConfiguration` не создаётся и не моделируется детально в версии `0.1`.

Причины:

- UI-прототип не должен знать формат реального движка;
- формат зависит от выбора Xray, sing-box или другого решения;
- преждевременная mock-конфигурация может закрепить неверный контракт;
- даже реалистичная тестовая конфигурация повышает риск случайного использования настоящих данных.

Граница конфигурации должна появиться после ADR по VPN engine и threat-model review.

## Интерфейсы, сохраняемые для будущего

Интерфейсы должны быть малыми и описывать необходимые возможности, а не будущую технологию.

### AuthRepository

В `0.1` обеспечивает:

- получение текущего mock-состояния авторизации;
- mock-вход;
- mock-выход.

Не включаются refresh tokens, OAuth, MFA, сетевые ошибки и реальные credentials.

### SubscriptionRepository

В `0.1` обеспечивает получение текущей mock-подписки.

Синхронизация, кеш, срок актуальности и получение по API откладываются до `0.2`.

### ServerRepository

В `0.1` обеспечивает:

- получение списка mock-серверов;
- получение сервера по synthetic ID, если это необходимо сценарию.

Проверка доступности, измерение задержки и получение конфигурации откладываются.

### SecureStorage

В `0.1` имитирует только сохранение и очистку synthetic session marker в памяти.

Интерфейс сохраняется, чтобы UI и сценарии не привыкали к прямому доступу к локальному хранилищу. Он не должен становиться универсальным key-value storage.

### VpnEngine

В `0.1` обеспечивает:

- начало mock-подключения для выбранных server ID и режима;
- остановку mock-подключения;
- получение или наблюдение за mock-состоянием;
- воспроизводимую безопасную ошибку.

Он не принимает настоящую `VpnConfiguration`, не запрашивает системные разрешения и не вызывает платформенные API.

Контракт real-подключения уточняется после выбора VPN engine. Публичная граница Core при этом сохраняется, а внутренние параметры порта могут быть расширены через ADR и контролируемую миграцию.

## Предлагаемая структура v0.1

Структура остаётся framework-agnostic:

```text
src/
  ui/
    screens/
    components/
    navigation/
    state/
  core/
    models/
    use-cases/
    ports/
    errors/
  adapters/
    mock/
  bootstrap/
tests/
  core/
  mocks/
  ui/
  fixtures/
```

Эта структура может быть каталогами внутри одного приложения. Создавать отдельный package/module для каждой папки не требуется.

Если выбранный фреймворк поощряет feature-first структуру, те же границы можно расположить внутри функций `auth`, `subscription`, `servers` и `connection`. Обязательным остаётся направление зависимостей, а не конкретные имена каталогов.

## Synthetic mock data

Все данные должны быть очевидно искусственными:

- идентификаторы используют префикс `mock-`;
- домены используют зарезервированную зону `.example`;
- при необходимости IP используются только документальные диапазоны;
- имена пользователей и серверов не копируют production;
- fixtures не создаются из дампов API, логов или screenshots реального сервиса;
- mock tokens и UUID не нужны и не должны генерироваться «для реалистичности»;
- ошибки содержат только фиксированные безопасные коды.

## Минимальная стратегия тестирования

До принятия ADR-006 необходим следующий минимум:

- unit-тесты допустимых переходов `Connection`;
- unit-тесты ключевых сценариев с mock-портами;
- проверка, что mock `VpnEngine` никогда не обращается к сети или платформенным VPN API;
- проверка основных UI-состояний;
- smoke-тест главного пользовательского пути;
- автоматическая проверка отсутствия запрещённых production endpoints и секретоподобных fixtures.

Полный набор adapter contract tests, integration tests и platform E2E tests откладывается до появления соответствующих адаптеров.

## Что откладывается до версии 0.2

- Реальная модель авторизации.
- Test API и HTTP-клиент.
- DTO и mapping сетевых ответов.
- TLS и проверка сертификатов в приложении.
- Реальные реализации защищённого хранилища.
- Refresh/revoke сессии.
- Синхронизация подписки и серверов.
- Offline/cache policy.
- Retry, timeout и rate-limit policy.
- Валидация недоверенных ответов API.
- Integration- и API contract tests.

Добавление этих частей требует security review authentication, storage и network.

## Что откладывается до версии 1.0

- Выбор и интеграция реального VPN engine.
- `VpnConfiguration` и правила её валидации.
- Android `VpnService`.
- Apple Network Extension.
- Desktop VPN adapters и привилегированные компоненты.
- Системные разрешения и уведомления.
- Background, reboot, sleep и network-change lifecycle.
- Reconnect, always-on и kill-switch policy.
- DNS, IPv4/IPv6 и routing leak protection.
- Разделение UI-процесса и VPN service/extension.
- Подпись и безопасное обновление VPN-движка.
- Платформенные integration и E2E tests.

Любая работа из этого списка требует отдельного security review и утверждённого ADR по VPN engine.

## Что нельзя откладывать или упрощать

Даже в `0.1` обязательны:

- отсутствие production-доступа;
- только synthetic mock data;
- граница между UI и внешними зависимостями;
- малый интерфейс `VpnEngine`;
- единый источник состояния `Connection`;
- отсутствие реальных секретов и конфигураций;
- безопасные фиксированные ошибки и логи;
- явная точка сборки зависимостей;
- возможность заменить mock-адаптеры без переписывания UI.

Эти ограничения дают основную ценность hexagonal architecture без стоимости полной production-модульности.

## Критерии готовности версии 0.1

Версия `0.1` архитектурно готова, если:

- все согласованные экраны и состояния доступны на выбранной первой платформе;
- основной сценарий проходит только через mock-порты;
- UI не импортирует конкретные mock-реализации;
- mock engine не создаёт сеть, VPN или системные разрешения;
- в репозитории нет production endpoints, токенов, UUID и конфигураций;
- connection state воспроизводим и протестирован;
- замена mock-репозитория технически возможна через Bootstrap;
- технологический стек и дальнейшие решения не представлены как принятые без ADR.

## Решения перед реализацией v0.1

До создания проекта необходимо утвердить:

1. первую целевую платформу;
2. технологический стек через ADR-001;
3. точный список экранов и navigation flow;
4. визуальные состояния mock-подключения;
5. перечень режимов подключения как UI-концептов;
6. минимальную стратегию тестирования либо временные критерии до ADR-006;
7. правила именования synthetic fixtures;
8. явный способ технически исключить production endpoints.
