# Architecture Decision Records

## Назначение

Architecture Decision Records (ADR) фиксируют значимые технические и процессные решения TerrieFlow Client вместе с контекстом, рассмотренными альтернативами и последствиями.

ADR нужны, чтобы:

- отделять принятые решения от предложений и предположений;
- сохранять причины выбора для одного разработчика и будущих участников;
- не пересматривать одни и те же альтернативы без новых фактов;
- явно фиксировать security-компромиссы и остаточные риски;
- понимать, когда и почему решение было заменено.

Общие документы архитектуры описывают направление. ADR отвечает на конкретный вопрос и фиксирует конкретный выбор.

## Когда создавать ADR

ADR требуется, если решение:

- влияет на несколько частей приложения;
- трудно или дорого изменить после начала реализации;
- определяет технологический стек или платформенную стратегию;
- меняет границы Domain, Application, Ports или Adapters;
- касается authentication, storage, network, VPN engine или конфигураций;
- влияет на безопасность, приватность или supply chain;
- определяет API, окружения, тестирование или выпуск;
- выбирает одну из нескольких разумных альтернатив с разными компромиссами.

ADR не требуется для:

- форматирования;
- локального переименования;
- мелкого рефакторинга без изменения поведения;
- временного mock-содержимого;
- решений, полностью определённых уже принятым ADR.

## Процесс принятия

1. Подготовить предложение и собрать факты.
2. Описать контекст, ограничения и варианты.
3. Провести security review, если решение касается authentication, storage, network, VPN engine, секретов или пользовательского трафика.
4. Представить черновик ADR на обсуждение.
5. Создать файл ADR только после явного подтверждения решения.
6. Добавить принятую запись в индекс.
7. При замене решения создать новый ADR и связать его с предыдущим.

Черновой анализ или список кандидатов не считается принятым ADR.

## Именование

Файлы именуются последовательно:

```text
NNN-short-decision-title.md
```

Пример:

```text
001-technology-stack.md
```

Номер не переиспользуется, даже если запись позднее отклонена или заменена.

## Формат записи

Каждый ADR использует следующий формат:

```markdown
# ADR-NNN: Название решения

**Дата:** YYYY-MM-DD
**Статус:** proposed | accepted | deprecated | superseded by ADR-NNN
**Участники решения:** ...

## Контекст

Проблема, ограничения и причины, по которым решение необходимо принять.

## Решение

Краткая и однозначная формулировка принятого решения.

## Рассмотренные альтернативы

### Альтернатива A

- Преимущества.
- Недостатки.
- Причина отказа.

### Альтернатива B

- Преимущества.
- Недостатки.
- Причина отказа.

## Последствия

### Положительные

- ...

### Отрицательные

- ...

### Риски и меры

- Риск.
- Способ снижения.

## Проверка решения

- Какие факты, прототипы или тесты подтверждают выбор.
- Когда решение следует пересмотреть.
```

## Жизненный цикл

```text
proposed -> accepted -> deprecated
                     -> superseded by ADR-NNN
```

- `proposed` — решение обсуждается и ещё не обязательно к исполнению.
- `accepted` — решение принято и является действующим.
- `deprecated` — решение больше не применяется.
- `superseded` — решение заменено новым ADR.

Изменять смысл принятого ADR задним числом нельзя. Для нового решения создаётся новая запись.

## Правило обновления индекса

После утверждения решения:

1. создаётся соответствующий ADR-файл;
2. запись добавляется в индекс принятых ADR;
3. тема удаляется из списка планируемых;
4. связанные архитектурные документы при необходимости получают ссылку на ADR, но не дублируют его обоснование.
